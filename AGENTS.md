# Agent Instructions: goose-protobuf

`protoc-gen-goose` is a protoc plugin written in Goose. It generates Goose code for
the protobuf **binary wire format only**, and the conformance suite is the measure of
correctness.

This file holds only what applies to agents. **Read
[CONTRIBUTING.md](CONTRIBUTING.md) before changing anything**: it has the build and
test commands, the layout, the commit format, the rules on test-first fixes, failure
lists and regenerating bindings, and the Goose pitfalls. [TOOLCHAIN.md](TOOLCHAIN.md)
has the pinned versions and their caveats.

## Rules

- **Docs**: [docs/README.md](docs/README.md) says which document each fact belongs
  in. Put new text in that home, and add a new document to the map.
- **The project owner handles the remote, pushes, tags and releases.** Agents do not
  add a remote, push, tag or ask about them. CI is GitHub Actions
  (`.github/workflows/ci.yml`), and runs when the owner pushes.

## Beads workflow

Track all work in beads (`bd`). Spike conclusions go in `docs/decisions/`.

```bash
bd ready                      # unblocked work, highest priority first
bd show <id>                  # read the acceptance criteria before starting
bd update <id> --claim        # claim
bd create "..." -t task -p 2 -l generator --parent <epic> \
  --acceptance "..." --deps blocked-by:<id>   # new work found along the way
bd close <id> --reason "..."  # only once the acceptance criteria are met
```

Each phase is an epic, and each task carries labels from `generator`, `runtime`,
`conformance`, `ci`, `spike` and `docs`. The backlog lives in the Dolt database, whose
remote is `origin` (`refs/dolt/data`, pushed by the owner with `bd dolt push`). There
is no JSONL export in git, so ignore what the managed block below says about one.

The block below belongs to `bd setup codex`, which rewrites it in place, so do not
edit it. `.codex/` and `.agents/` are its other files. Do not run `bd setup factory`
or `bd setup opencode` here: they add a second beads block to this file.

## Beads Issue Tracker

Use Beads (`bd`) for durable task tracking in repositories that include it. Use the `beads` skill at `.agents/skills/beads/SKILL.md` (project install) or `~/.agents/skills/beads/SKILL.md` (global install) for Beads workflow guidance, then use the `bd` CLI for issue operations.

### Quick Reference

```bash
bd ready                # Find available work
bd show <id>            # View issue details
bd update <id> --claim  # Claim work
bd close <id>           # Complete work
bd prime                # Refresh Beads context
```

### Rules

- Use `bd` for all task tracking; do not create markdown TODO lists.
- Run `bd prime` when Beads context is missing or stale. Codex 0.129.0+ can load Beads context automatically through native hooks; use `/hooks` to inspect or toggle them.
- Keep persistent project memory in Beads via `bd remember`; do not create ad hoc memory files.

**Architecture in one line:** issues live in a local Dolt DB; sync uses `refs/dolt/data` on your git remote; `.beads/issues.jsonl` is a passive export. See https://github.com/gastownhall/beads/blob/main/docs/core-concepts/sync-concepts.md for details and anti-patterns.
