# 0019: edition 2026 is supported

- Status: accepted
- Date: 2026-11-06
- Bead: gpb-ky7.19
- Toolchain: Goose v2026.3, protoc 36.2, linux-x64
- Builds on: [0014](0014-protoc-range.md) (protoc range),
  [0016](0016-edition-2024.md) (edition 2024)

## Question

protoc 36.2, the pin, takes `edition = "2026"` and asks the plugin, which refused it. So
a user on the pinned protoc could write such a file and have no way to generate code.
What does the edition change, and can the plugin take it?

## What the edition changes

Compared with edition 2024, from `descriptor.proto`, `protoc --edition_defaults_out` and
protoc's `descriptor.cc`:

| Change | Effect on the plugin |
|---|---|
| The defaults of `field_presence`, `enum_type`, `repeated_field_encoding`, `utf8_validation` and `message_encoding` | None: all five are unchanged, and they are all the wire format reads |
| `enforce_naming_style` defaults to `STYLE2026`, which also refuses names that collide in generated code | None: protoc enforces it, and a file that breaks it never reaches the plugin |
| `default_symbol_visibility` defaults to `STRICT`: everything is local unless exported, and a nested type cannot be exported | None: protoc enforces it, and types are generated the same |
| `enforce_proto_limits` defaults to `PROTO_LIMITS2026`: at most 1500 fields in a message, 1000 oneofs in a message, 1200 fields in a oneof and 1700 values in an enum | None: protoc enforces it, and the plugin has no such limits |
| `cc_enable_arenas` is removed | None: the plugin does not read it |

So the change is one number in the plugin's response, and the table it is tested
against. `STYLE2026` is stricter than the plugin's own collision check, and the plugin
still makes that check, as a file can opt out with `STYLE_LEGACY`.

## Evidence

- `tests/protos/editions_2026.proto` uses all of the above that a file can show. A golden
  and a round trip through protoc and Python hold it.
- `tests/selfhost/feature_defaults_unit.goose` holds that protoc resolves edition 2026 to
  the same five values as edition 2023.
- **The conformance suite has no edition 2026 message**, so `--maximum_edition 2026` runs
  exactly what 2023 does, and shows only that nothing regressed.
- So the real test was run once, by hand, as for decision 0016: the suite's three
  edition 2023 files recompiled as edition 2026, with `ctype` and `java_multiple_files`
  taken out, and legacy names and `EXPORT_ALL` set for the file. It gave the same 2832
  successes, and with recommended tests the same one listed failure, so the failure lists
  did not grow.
- protoc 35.1 refuses such a file with its own error, and 36.0 and 36.2 take it.

## Decision

**The plugin takes edition 2026.** Edition 2026 files need protoc 36.0 or later. Older
releases in the range of decision 0014 still refuse such files with their own clear
error, and still take everything else, so the range does not change.
`scripts/protoc_versions.sh` leaves the 2026 tests out below 36.

Generated code for edition 2026 uses the same public names, so this is a minor by
decision 0012.

No released protoc in the range now asks the plugin for an edition it refuses, as 36.2 has
2026 as its maximum. A later protoc may have a newer edition, which the plugin will refuse
until it is looked at in the same way.

## If the suite gains a message

As in decision 0016: the testee should then handle it, and the one-off is no longer
needed.
